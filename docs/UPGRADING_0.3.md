# 升级到 Iris 0.3.0

0.3.0保留原生DSH插件与独立CLI，加入独立Core工作台、通用MCP、持久媒体流程、网络出口、有界调度和显式插件。安装前核对准确版本是否已发行；发布准备期间使用源码或本地候选包，版本号本身不证明npm已经发布。正式发行更新npm `latest`；需要固定环境时使用准确版本，不依赖移动渠道。

## 升级前

- 使用Node.js **≥22.1.0**；0.2.7的22.0.0最低要求不适用于0.3.0。DSH要求更高时以宿主为准。
- 确认实际Iris版本、目标DSH profile或独立项目，以及数据根、私有供应商配置、认证和连接档案的位置。DSH沿用[12个准确版本声明](DSH_COMPATIBILITY.md)，未扩大宿主支持范围。
- 等待在途操作结束，再正常停止将要升级的写者；保留配置、数据根及根外认证/连接档案的独立备份。不要删除租约、任务或旧工作区。
- 记录已受理或受理未知任务的原UUID与结果状态。升级、刷新和重连不授权重新生成；先查询原任务。

## 从0.2.7升级

正式版本已发行后，选择对应入口：

```bash
# 原生DSH插件：替换为已经确认的profile
dsh plugin --profile web add @mokuyoaxis/dsh-iris@0.3.0

# 独立CLI/Core：在使用Iris的项目中更新
npm install @mokuyoaxis/dsh-iris@0.3.0
npx dsh-iris --help
```

DSH按正常流程重载插件后端并刷新客户端，不擅自重启其他任务。旧DSH/CLI配置和数据继续按原入口使用，不会因包升级变成新Core执行根，也不会自动开启能力、补齐空池或授权目录新模型。

需要Web/MCP时，按[Core快速开始](CORE_QUICKSTART.md)选择**新的私有根**，先`flow init`，再`execution init --vision`建立v5执行根。不要在已有0.2.x根、非空目录或日常DSH数据根上尝试初始化；本版本没有统一迁移工具。按需显式配置模型、私有凭据和客户端授权，不自动复制其他宿主的密钥。

| 原有状态 | 0.3.0中的处理 |
| --- | --- |
| DSH/CLI传统Task与Artifact根 | 保留原入口和数据；新Web不自动导入 |
| v0只读Flow根 | 保持原能力；不就地转换为执行根 |
| v1/v2/v3/v4执行根 | 保持各自能力；新增功能需另建对应根 |
| 新v5执行根 | 支持图片、语音/转写、固定文生视频及看图/OCR；仍需模型和明确授权 |
| 已保存MCP连接 | 保留原工具/权限选择；包升级不自动增加vision/ocr或写权限 |

## 从0.3预发布升级

beta.1至beta.3的Node最低要求已是22.1.0。正式版沿用最小插件契约、持久格式和显式授权边界；已有合适版本的根可以继续使用，不因正式版标签自动变成v5。准确兼容范围不包含0.3.0的第三方插件仍会被拒绝，应由插件维护者核对后更新声明，不绕过版本检查。

beta.3之后的维护改善DSH拒绝诊断及MCP串行执行/只读恢复指引。它没有增加自动重试、迁移或权限。`root_busy`不等于已排队；以原UUID核对Operation和Task，再决定下一步。只读连接查回Operation时，Core仍需运行提供这些读取路由的服务，不能仅凭连接的read授权开启服务。

## 升级后核对

1. 核对实际包版本、Node、CLI帮助或DSH Doctor及插件装载状态。
2. 先只读查回已有Task/Artifact；需要Core时检查所选根的版本、原Run/Operation和登录/连接状态。读取与恢复不应重新生成。
3. 核对供应商、模型用途、功能池和网络出口。目录可达不等于模型可用；显式出口失效不应悄悄直连。
4. 只有在用户明确要求后，再对选定模型做一次受控范围的实际媒体操作；记录原UUID及交付结果。模型调用可能计费。

回退包版本不等于回退数据格式。旧CLI不能写新执行根；若需要旧环境，应使用对应旧根或独立备份，不让新旧写者同时操作同一根，也不覆盖当前数据。

## 本次保留的限制

OCR重叠块未去重，完成状态不保证唯一全文或识别准确率；见[验证记录](OCR_VALIDATION.md)。PRoot历史停顿原因仍在调查。Core音乐、完整SDK冻结、真实ComfyUI GPU和全部平台/宿主认证继续后置，见[范围约定](BETA_SCOPE.md)。新实时语音/图片翻译型号也不代表对应新协议已经适配。
