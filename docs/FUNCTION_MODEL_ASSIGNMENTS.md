# 功能模型分配

版本要求：Iris0.2.4。0.2.3只有Music采用严格名单；本页说明升级后的统一规则，发布状态见 [README](../README.md)。

在“功能分配（调用顺序）”中为图片、视频、语音、音乐、转写和视觉分别选择模型。模型池登记资源、能力、协议和健康；只有加入功能名单的模型参与该功能的新请求。普通模型使用 `providerId::modelId` 复合引用，同名模型的不同账号独立选择。

每次请求按名单顺序选择。已停用、缺少配置、已知冷却或不支持本次模式的项可跳过；名单之外的模型不会补入。临时指定模型也必须属于名单，且本次只调用指定项；失败不会改用其他模型。没有分配或名单全部不可用时明确失败。

“清空分配”停止该功能的新调用，保留供应商、模型池、任务和作品。修改名单影响后续请求；原任务的观察和补交付仍绑定原模型和协议，不按新名单重新生成。原供应商停用、移除或绑定漂移时，仍可能无法恢复。

## 功能范围

- 图片生成与改图共用图片名单；改图只保留支持编辑协议的候选。
- 视频与S2V共用视频名单，按实际首帧/音频输入筛选。
- 看图、OCR、定位和视觉摘要共用视觉名单。
- TTS、Music和转写各自分配；本地裁剪、抽帧等不需要模型。
- 提示词优化继续使用独立文本路由，不随媒体分配改变。

媒体生成仍只在明确未受理时切换候选。已受理或未知状态停止自动换模型；Vision沿用已有有限候选策略。Music的显式有限502重试维持原规则，可能消耗额外额度，每次创建关联新任务。

## DSH宿主视觉

视觉名单可加入并排序“DSH 当前默认模型”，引用为 `host:current-vision`。它通过宿主默认选择及精确元数据绑定，只有声明支持图片输入才调用；不宣称使用当前对话所选模型。一轮OCR或其他复合操作复用已绑定的实际模型，默认设置变化影响下一次操作。

宿主视觉只有明确加入名单才参与，不自动放在自持模型之后。临时指定该项时也只使用该项。独立CLI没有DSH宿主，不能执行此资源；需分配可由CLI直接调用的Provider模型。

## 从旧行为升级

原来依赖“自动按模型池顺序选择”的功能需要明确分配。已有明确名单及顺序继续保留，升级不自动复制整个模型池、不修改个人配置。未填写和空名单均表示未分配；模型停用后仍可在分配页看到原选项及不可用状态。

已有手动模型实测独立于生产名单，按既有确认与支持范围执行；实测成功更新健康状态，不自动分配。发现模型、查看状态和编辑标签不会发起生成。

Headless配置示例：

```json
{
  "providers": [
    {
      "id": "provider-a",
      "auth": "none",
      "baseUrl": "http://127.0.0.1:8080/v1",
      "mediaProtocol": "openai-images",
      "models": [
        {"id": "image-a", "capabilities": ["image-gen"]},
        {"id": "vision-a", "capabilities": ["vision"]}
      ]
    },
    {
      "id": "provider-b",
      "auth": "none",
      "baseUrl": "http://127.0.0.1:8081/v1",
      "mediaProtocol": "openai-images",
      "models": [{"id": "image-b", "capabilities": ["image-gen"]}]
    }
  ],
  "assignments": {
    "image-gen": ["provider-a::image-a", "provider-b::image-b"],
    "vision": ["provider-a::vision-a"]
  }
}
```

示例引用的账号和模型必须实际存在、启用并声明对应能力。配置操作与参数见 [CLI管理](CLI_MANAGEMENT.md)。
