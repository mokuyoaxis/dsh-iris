# 文件访问与跨环境

记一下 iris 在不同宿主环境下"怎么拿到用户文件"这件事的判断，以及在开发机上实测的结果。它直接决定了文件选择器该怎么设计。

## 为什么会纠结这个

开发机是 Android 上跑的 Debian（proot），DSH 和 iris 都在这个 Debian 里。但真实用户大概率在 Windows 桌面、原生 Linux 或 WSL 上。iris 的工具（看图、裁剪、转写、抽帧这些）要读用户指定的文件，而"宿主到底能不能读到那个文件"，在不同环境下差别很大——这一点很容易被忽略，因为在我们这台机器上它恰好是通的。

## 一条主线

拿用户文件有两条路，性质完全不同。

一条是**把文件字节送进宿主**：浏览器读文件、POST 给 iris、落到宿主自己一定读得到的目录。这条路和拓扑无关——浏览器就是用户本机的原生文件浏览器，它能在哪读到文件，字节就从哪来，宿主压根不需要知道那个文件原本在哪。

另一条是**把路径交给宿主**：手输路径、工作区索引、工具现有的 `*_path` 参数，都是让宿主直接 `readFile` 那个路径。这条路把"文件在哪"和"宿主能看见什么"焊死在一起，一旦两者的文件系统视图不一致就断。

结论其实就一句话：上传解耦了这两件事，路径没有。

## 各环境的差别

原生 Linux 和原生 Windows 上，浏览器和宿主看的是同一套文件系统，两条路都通，没什么好说的。

WSL 要留神。DSH 跑在 WSL 里，宿主能读 Windows 文件，但得走 `/mnt/c/...` 这种翻译路径，而用户脑子里想的是 `C:\...`。更麻烦的是，如果浏览器是 Windows 侧的（WSL 里通常没有图形浏览器），它选中的文件根本不在 WSL 的文件系统上，只有把字节传过去才够得着。

Android 加 Debian 最不确定。宿主能不能读安卓的共享存储，全看这台机器的 proot 有没有把 `/storage/emulated/0` 挂进来、以及安卓的分区存储给不给权限。换一台设备，同样的路径可能就是"文件不存在"。

## 实测

在开发机上做了两个。

第一个，让宿主直接读安卓 Download 目录里的一张图去识图。这台机器恰好把共享存储 bind-mount 进来了，本进程也有读权限，于是识图成功，画面内容也描述对了。但这属于侥幸——它依赖这台机器的挂载和权限配置，不能当成可移植的能力。

第二个，浏览器截一张图存到宿主可读的目录（`/tmp` 之类），再让 iris 识图。这个干净地成功了，而且模型把截图里"泡泡工作台"设置页的界面元素都读了出来。这条路径正是上传的模型：字节落在宿主一定读得到的地方，没有跨文件系统的麻烦。

顺带一提，识图用的是发现动作从 `/models` 拉进池的那个 qwen3-vl 模型，说明模型池发现确实在起作用。

## 所以文件选择器怎么定

把上传和"选会话附件"当默认主路，它们在四种环境下都成立，用户也不用懂路径。手输路径降级成高级项，并且老实标一句"这是宿主文件系统路径"——因为在 WSL 和安卓上，宿主看到的东西跟用户在文件管理器里看到的根本不是一回事。

手输路径不删，是因为它有一个上传替不了的用处：几个 G 的大视频，上传要复制字节、还受大小上限，而在原生或 WSL 下直接给路径不复制、更快。所以是"默认上传、大文件走路径"，不是二选一。

这么看，FileField 不只是省得打字，它其实是跨环境下的正确性修复：把用户的文件落到宿主确实读得到的 `uploads/`，工具才真能用。

## 发布前还要盯的几件事

- 上传的文件落在 `uploads/`，在安卓上位于 proot 的应用私有区，宿主读得到、但用户在系统相册里翻不到。这没关系，读它的是 iris 不是用户。
- 大文件经 WSL2 或安卓的 localhost 转发会很慢，现在 64MB 的上传上限要不要按图片/视频分档，待定。
- iris 全程用 `path.join`、`path.isAbsolute`，Node 在 Windows 下能处理盘符和反斜杠，但我还没在真 Windows 和 WSL 上实跑过，发布前这两处各跑一遍冒烟。
- 安卓的 SAF 选文件常给 `content://` 而不是文件路径。上传不受影响（浏览器已经把字节交出来了），但"直接引用安卓路径"这条路走不通——又一个该优先用上传的理由。
